1. Project Overview

JobKhoj is a single-page application implementing a complete job-portal workflow for three roles: job seeker, recruiter and administrator. The interface, business rules, routing and data layer are fully built; the persistence layer currently runs on a seeded in-memory mock database that mirrors a REST API, so the app can be switched to a live Spring Boot backend by changing one environment variable.

3. Architecture

The code follows a layered structure: pages never touch storage directly — they call services, the service layer chooses mock or live, and mock handlers own all business rules.

— Page / Component  (React, hooks, rendering)
        ↓  module import
— Service layer    (authService, jobService, adminService …)
        ↓  picks mode at runtime
   → mock handler  → in-memory DB  ↓  (seed data)
   → Axios client → http://localhost:8080/api

5. Data & Mock Layer

A deterministic in-memory database behaves like a REST API, so the UI can be developed and tested before the backend exists.

Handlershandlers/ — auth, jobs, companies, applications, users, recruiter, admin, query, index, latencyBusiness rules: search & facets, pagination, moderation transitions, pipeline stage moves, role checks, artificial latency

5.1 Domain rules implemented in the mock layer

  • Moderation lifecycle — companies Pending → Verified / Rejected / Suspended, jobs Pending Approval → Active / Rejected, users Active → Blocked.
  • Recruiter Kanban pipeline — Applied → Screening → Shortlisted → Interview → Selected → Hired, with a terminal Rejected column counted separately.
  • Status change updates both the recruiter's stage and the seeker's visible status, and appends a timeline entry.
  • Blocked accounts are excluded from dashboards and queues.
  • Company ownership is resolved from the session, not from the request body, so a recruiter cannot edit another company.

5.2 Status vocabulary (single source of truth)

Constant groupValues
ROLESJOB_SEEKER, RECRUITER, ADMIN
APPLICATION_STATUSApplied, Under Review, Shortlisted, Interview, Rejected, Hired
JOB_STATUSDraft, Pending Approval, Active, Closed, Rejected, Expired
COMPANY_STATUSPending, Verified, Rejected, Suspended
USER_STATUSActive, Blocked
PIPELINE_STAGEAPPLIED, SCREENING, SHORTLISTED, INTERVIEW, SELECTED, HIRED, REJECTED
NOTIFICATION_TYPESHORTLISTED, INTERVIEW, MATCH, STATUS
Enforced by tooling: an ESLint rule bans these values when written as raw string literals, so status values can no longer drift away from the constants. This closed a real class of bug where 'VERIFIED' (uppercase) was written while the constant is 'Verified' — which silently returned zero rows from every filter.

6.4 Known limitation

There is no browser-level (end-to-end) test harness in this project. The automated suite verifies data behaviour and that every screen renders, but interactive flows such as clicking through an application, submitting forms or drag-and-drop have not been exercised by an automated browser test.
